2-party VDMPF scheme.

Gen() and CPU evaluation are host operations. Cuckoo hashing uses exactly three candidate buckets per input. The PRP permutes [0, 3*kDomainSize), where kDomainSize = 2^in_bits. kBucketCount is the allocated bucket count for max_points. Gen() returns the active bucket count m_rt and bucket-domain size b_size_rt for the actual point count. These runtime values, the PRP seed, and all per-bucket arrays must come from the same successful Gen() call. Evaluation derives its bucket bound from b_size_rt, so it needs b_size_rt but not m_rt; m_rt stays key metadata. kBucketCount is also the proof-fold range: the proof loops fold every allocated bucket, and the loops not involved in the fold use the bound derived from b_size_rt. No entry receives a bucket count. The supported point-count interval is [kMinPoints, max_points]. Increasing bucket_bits can lower kMinPoints at the cost of more correction word storage. BatchEval() uses chain accumulation and BatchEvalMerkle() uses a Merkle fold. Both parties must use the same accumulator, key configuration, and query sequence. XorHash receives (packed within-bucket index, clamped leaf seed), in that order. The index uses the full coordinate block; bit 0 of the seed's fourth word is reserved and passed as zero. The built-in backends use that seed bit for digest tags. Verification guarantees require the assumptions and accumulator-specific proof conditions in doc/vdpf_merkle_fold_security.md. EvalAll() and EvalAllMerkle() use the same accumulators for the full domain in increasing input order. Eval() evaluates one input per call and returns the proof material for Prove() (chain) or ProveMerkle() (Merkle). The per-input methods share the fused paths' bucket-level folds; with the same key and query sequence they produce the same proofs, and the same shares for the commutative Group backends in this repository.

Batch verifiable evaluation method.

Evaluates caller-owned correction words and party seeds on a batch of inputs, producing shares and a chain proof.

Inputs in xs must lie in [0, 2^in_bits). The sequence may be sparse, unsorted, or contain repeated inputs. Both parties must use the same sequence, including its order and length, and the same proof accumulator and hash configuration. Both servers must obtain the same xs by a path the client cannot split. Any verification guarantee is restricted to the evaluated input values and requires the scheme's security assumptions. See doc/vdpf_merkle_fold_security.md for assumptions and instantiation limits.

Batch evaluation method with the Merkle-fold proof.

Parallel-friendly alternative to BatchEval(): same output shares, and the proof replaces the paper's sequential chains with Merkle-style folds. Per bucket, the leaf nodes (hashes of the corrected per-point hashes, ordered by query position, then hash-function index) form one canonical Merkle tree. Adjacent nodes combine level by level, carrying an odd trailing node unchanged. The bucket node hashes the concatenation of its hashed cs and its tree root. An empty bucket contributes only its hashed cs. The kBucketCount bucket nodes fold the same way into the final proof, whose last two words stay zero. Execution block sizes and GPU work partitioning do not change this tree or the proof. Every combining step hashes 64B to 32B, so fold binding for a common ordered query sequence and tree shape reduces to the pairwise collision resistance of the fold hash. Share integrity also requires the remaining assumptions in doc/vdpf_merkle_fold_security.md.

The proof keeps the 64B shape, so Verify() is shared, but chain and fold accumulators produce different proofs: both parties must pick the same one. This host path is the sequential reference; the GPU path folds the same construction and matches it bit-exactly.

Inputs in xs must lie in [0, 2^in_bits). The sequence may be sparse, unsorted, or contain repeated inputs. Both parties must use the same sequence, including its order and length, and the same proof accumulator and hash configuration. Both servers must obtain the same xs by a path the client cannot split. Any verification guarantee is restricted to the evaluated input values and requires the scheme's security assumptions. See doc/vdpf_merkle_fold_security.md for assumptions and instantiation limits. Each occurrence of a repeated input contributes its own candidate records and one leaf per record.

Launch batch Merkle evaluation of an arbitrary ordered query sequence.

The outputs and proof match host BatchEvalMerkle() bit for bit on the same ordered xs, for any query sequence: sparse, unsorted, or duplicated. The order of xs is part of the contract; both parties must pass the same sequence and agree on the Merkle accumulator. Chain accumulation over a query sequence stays on the host, in BatchEval(). Every input pays its own three located-bucket walks, one per Cuckoo candidate, as in the host batch path; no tree walk is shared across inputs.

Takes the raw key components sigma, b_size_rt, s0s, cws, and cs as Gen() returned them and prepares what the kernels need internally. The host instance passes backend values as kernel arguments. Referenced backend resources and device buffers are prepared and retained by the caller. Temporary work arrays and CUB sorting storage are allocated and released internally using CUDA stream-ordered allocation on stream. The CUB size query runs before allocation. No backend upload, deep copy, event management, or host/device synchronization is performed. The Prp backend must be device-callable: ChaChaFeistel qualifies; Aes128Feistel and Aes128FeistelRaw are host-only and fail to build with an unresolved-extern error when used on device.

Inputs in xs must lie in [0, 2^in_bits). The sequence may be sparse, unsorted, or contain repeated inputs. Both parties must use the same sequence, including its order and length, and the same proof accumulator and hash configuration. Both servers must obtain the same xs by a path the client cannot split. Any verification guarantee is restricted to the evaluated input values and requires the scheme's security assumptions. See doc/vdpf_merkle_fold_security.md for assumptions and instantiation limits. Each occurrence of a repeated input contributes its own candidate records and one leaf per record.

Evaluate one input and return the corrected per-point hashes for Prove() or ProveMerkle().

The per-input counterpart of the fused evaluation: with the same key and the same query sequence, Eval() per input followed by Prove() produces the same chain proof as one BatchEval() call, and by ProveMerkle() the same Merkle proof as one BatchEvalMerkle() call. The proofs do not depend on the group order. Shares match the fused paths for the commutative Group backends in this repository: Eval() adds one input's candidate shares in candidate order, while the fused paths add them in bucket order.

Routing covers every bucket below the bound ceil(3*kDomainSize/b_size_rt) derived from b_size_rt. Under a key from the same successful Gen(), b_size_rt = ceil(3*kDomainSize/m_rt) keeps every candidate below that bound, which is at most m_rt, so an inactive bucket cannot receive a candidate. Inactive buckets still take part in the accumulators through their correction seeds: Prove() folds each bucket's cs and ProveMerkle() folds each bucket's hashed cs.

Generate shared correction words with read-only seeds and one attempt.

Makes one Cuckoo-hashing attempt and one attempt for each inner VDPF. Caller-owned sigma and s0s are preserved.

Retrying a failed attempt
On return 1, draw a fresh uniformly random sigma block from a cryptographically secure random generator. Keep s0s unchanged because placement does not depend on the inner VDPF seeds. On return 2, keep sigma and draw fresh independent uniformly random seed pairs for all kBucketCount buckets from a cryptographically secure random generator. The bucket containing the failed inner VDPF is not reported. Both inner VDPF failure conditions use this same resampling procedure. In either case, rerun the whole Gen with the same points and payloads. Incrementing seed words is not resampling. The caller chooses the attempt limit and handles exhaustion. Reuse of the output buffers is allowed, but discard all cws and cs from the failed attempt, including completed buckets. Only outputs and input seeds from a successful call form a usable key.

Proof accumulation method for the per-input evaluation.

The per-input counterpart of BatchEval(): accumulates the corrected per-point hashes of Eval() into the chain proof with the same per-bucket and cross-bucket folds as the fused path. With the same key and the same query sequence, Eval() per input followed by Prove() gives the same proof as one BatchEval() call, and the same shares for commutative group addition.

Bucket ids and candidate indices are re-located from sigma, b_size_rt, and xs, so proof_values stores corrected hashes only. Both parties must supply the same xs order and the same accumulator. Chain and Merkle accumulators must not be mixed: Prove() and ProveMerkle() produce different proofs from the same values.

Inputs in xs must lie in [0, 2^in_bits). The sequence may be sparse, unsorted, or contain repeated inputs. Both parties must use the same sequence, including its order and length, and the same proof accumulator and hash configuration. Both servers must obtain the same xs by a path the client cannot split. Any verification guarantee is restricted to the evaluated input values and requires the scheme's security assumptions. See doc/vdpf_merkle_fold_security.md for assumptions and instantiation limits.

Estimate the number of buckets for three-choice Cuckoo hashing.
Definition cuckoo_hash.cuh:245

Smallest point count supported by this bucket_bits configuration.

Gen() accepts every t in [kMinPoints, max_points]. The lower bound is at least 30, where the Cuckoo bucket-count estimate applies. Fewer points use fewer buckets and can require a larger per-bucket domain. The capacity condition is ceil(3*kDomainSize/ChBucket(t, ch_lambda)) <= 2^bucket_bits. The shared buffer of correction words contains kBucketCount*(bucket_bits+1)*sizeof(Cw) bytes, so each extra bucket bit adds kBucketCount*sizeof(Cw) bytes without changing the bucket count.

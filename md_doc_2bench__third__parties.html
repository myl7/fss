Benchmark runner and third-party comparisons

The native suite and third-party adapters use in_bits=20 by default, a domain of 1,048,576 inputs. See benchmark methodology and comparison curves for the current adapters, additive uint128 DCF measurements, and domain sweeps.

N is the domain size, T is the CUDA threads per block, and K is the number of keys processed per benchmark iteration or call. Keys per launch is an additional count. In kernel<<<grid_dim, block_dim>>>, block_dim sets the threads per block. The key count and domain size do not specify this launch parameter.

Running

The reproducible runner is third_party/bench.py. It supports list, prepare, build, run, and summarize. All build trees, environments, caches, logs, and results are under the repository's build/third_party/ directory.

The supported environment is Linux x86_64 with an NVIDIA GPU for GPU runs. Select an idle CPU and GPU on a shared host. The fss and raw AES CPU wrappers also require a CUDA toolkit because their sources include CUDA headers and device code. Rust, libfss, Google DPF, GPU-DPF CPU, and fss 0.7.0 CPU can be selected independently. CPU AES-NI cases require an AES-capable processor.

Install a C++ compiler, CMake, OpenSSL, GMP, MPFR, Eigen3, taskset, Rustup, Bazelisk, and uv. The full suite uses the CUDA toolkit's runtime, cuRAND, and headers. For Ubuntu 24.04, the development packages are:

sudo apt-get install build-essential cmake libssl-dev libgmp-dev libmpfr-dev libeigen3-dev util-linux

GPU-DPF pins Python 3.11.16, PyTorch 2.10.0+cu130, NumPy 1.26.4, setuptools 80.9.0, Ninja 1.13.0, and uv 0.12.24 in its project and lockfile. It requires a CUDA 13 toolkit and a driver compatible with that PyTorch wheel. The runner bootstraps the pinned uv version into build when required. It builds the extension from a copy of the pinned source and applies any checked-in compatibility patches to that copy. The submodule stays at its recorded commit.

The other source versions are fixed by Git submodule entries, Cargo lockfiles, Rust toolchain files, and Bazel's module lockfile. Google DPF uses Bazel 7.6.1. dpfplusplus is the exception to vendoring: its headers are an anonymous pre-release that forbids redistribution, so prepare clones it on demand under build/third_party/dpfplusplus/, checks out the pinned commit, and applies three documented text fixes before the wrapper compiles against it; no upstream byte is committed. See bench-dpfplusplus.md for provenance, license status, and reproduction steps. The mastic, plasma, and sycret entries build on the Rust stable toolchain through the same pinned RUST map that libdpf uses. Each CMake wrapper uses Google Benchmark 1.9.5, while Google DPF uses 1.8.3. prepare initializes selected submodules recursively and installs the pinned Rust toolchains and GPU-DPF environment. It does not run EzPC's setup script, which also builds unrelated applications and downloads datasets. The EzPC dependency wrapper uses upstream sytorch/random.cpp, cryptoTools, bitpack, and LLAMA. It preserves their crypto and random-number implementations while omitting unused SCI/SEAL and neural-network backends. GPU RNG and AES remain the pinned EzPC CUDA implementations. Its compile commands and link map are saved with the build.

Run the native suite

Build the native binaries with -DBUILD_BENCH=ON and run them directly, or use the Makefile to select a CPU and GPU through the runner:

CPU_ID=0 make bench_cpu
GPU_ID=1 CUDA_ARCH=86 make bench_gpu

Select idle devices allowed by your host. Direct binary invocations leave CPU affinity and the governor to the caller. Both Makefile targets use the decision profile by default. Set BENCH_PROFILE=publication BENCH_WORKLOAD=legacy to restore historical sampling and full-domain workloads. Set CUDA_ARCH only when CMake cannot infer it.

Native benchmark coverage

bench_cpu and bench_gpu cover DPF, DCF, VDPF, Half-Tree DPF, packed Half-Tree DPF, Grotto DCF, Half-Tree Grotto DCF, DMPF, and VDMPF. The CPU suite compares OpenSSL AES, AES-NI, software AES, and ChaCha PRGs. The GPU suite uses the device-callable software AES and ChaCha backends. The suite also measures VDPF proof aggregation, Grotto preprocessing, and independent-key GPU batches. Internal compact point-evaluation experiments are separate from the public Eval rows and are not public APIs.

Native names identify the scheme, operation, output group, PRG, and domain bits. For example, BM_DcfEval_Uint_AesRaw/17 evaluates DCF over a 2^17 domain with the Uint group and AES-NI PRG. PRG suffixes are Aes for OpenSSL, AesRaw for AES-NI, AesSoft for software AES, and ChaCha. Grotto rows omit the output group because they produce F2 shares.

A batch row times the whole API call, while its item counter may count keys, queries, or domain outputs. Packing and other preparation may happen outside the timed call. Check the timing boundary and denominator before comparing throughput or deriving latency per item.

Run profiles

Both Python runners resolve a shared profile through third_party/benchmark_policy.py. Explicit --min-time and --repetitions values (and --warmup on the figure runner) always override the profile timing, and explicit selection arguments always override the profile selection.

Profile Timing defaults Selection defaults
decision (default) 0.3 s minimum measurement, one repetition, no extra warmup current library only: --libraries main for bench.py; the FSS wrapper at n = 8, 20 on the figure runner
smoke 0.01 s, one repetition current library, full-domain rows included
publication bench.py: 1 s and five repetitions; figure runner: 0.1 s measurement, 0.1 s warmup, five repetitions each runner's historical default selection

--smoke remains an alias for --profile smoke; combining it with a different explicit profile fails. The decision default excludes the internal compact-path and point-launcher experiment rows (names containing EvalPoint) from the main library; an explicit --filter and the publication profile keep the full selection. The filters are plain POSIX extended alternations over the registered operation names, because the native binaries compile --benchmark_filter with a regex backend that rejects lookaround. Smoke includes the full-domain rows instead of excluding them, so one correctness run covers at least one real n = 20 full evaluation. Explicit --min-time and --repetitions values reach the native commands unchanged in every profile, including smoke. When the resolved repetitions exceed one, the current library's native commands (main and the FSS wrapper) run their repeated samples with Google Benchmark random interleaving, one --benchmark_enable_random_interleaving=true per command; a single repetition, third-party adapters, and the historical FSS binaries carry no such flag. An explicit --benchmark_enable_random_interleaving=false|true after -- overrides the mode for the run, is resolved before --plan prints, and the command carries exactly one such flag. Interleaving shuffles the repetitions of the rows selected within one native command; it does not interleave independent processes, binaries, or cases, and is not a global A/B schedule or a precision guarantee. The resolved mode is recorded per command in --plan and the run manifest.

--plan prints the resolved libraries, exact filters, timing budget, and work configuration without building or touching hardware. A --benchmark_filter= value passed after -- is folded into the plan before it is printed, so the plan always shows the exact filter the run would use. The native result-row count is printed as unresolved because it is known only after the run.

Full-domain launch control

The main GPU batch full-domain rows process the 2^20-key fixture through 1024-key API calls. The fixture's alphas and evaluation points are masked to the configured input domain, and the receipt records that fixture domain. --workload daily (default) runs one full API call per iteration, --workload legacy restores the historical 1024 calls per iteration, and --full-launches N selects 1 to 1024 calls explicitly. The runner forwards the resolved value through FSS_BENCH_FULL_LAUNCHES and records it in the run manifest and --plan; the executed calls_per_iteration and batch_keys counters are checked against that plan, and batch keys stay 1024. The four batch full-domain rows (DPF, DCF, HalfTree DPF, packed HalfTree DPF) must carry both counters; a receipt missing either fails the run. The single-key full-domain rows (Grotto DCF, VDPF Merkle) are exempt. --workload legacy conflicts with an explicit --full-launches other than 1024. The daily row keeps real batch throughput semantics with a workload identity different from the legacy row, and its 1024-key batch cost divided by 1024 is an amortized per-key cost, not single-key latency.

New main and FSS receipts carry per-iteration work counters with work_schema_version = 1; a new main or fss collection whose receipts lack the marker fails instead of falling back to the legacy reading. The runner normalizes them as time per iteration divided by work per iteration, keeps logical output counts, output bytes, proof counts, proof bytes, point-hash bytes, and GPU host wall time in separate summary columns, and records the process wall time per command separately. The work unit names the primary metric: keys or PRG calls, queries, domain outputs, prepared leaves for preprocess rows, or proofs for proof rows. Proof rows report their real zero keys and zero logical output bytes with the proof count and proof bytes in their own columns, and leave the key columns empty, because they process no keys. output_bytes counts logical output storage bytes, not DRAM traffic; proof_bytes counts final proof storage; point_hash_bytes counts the raw corrected per-point hash material Eval stores, which is the input to Prove, not a proof. The main GPU VDPF point rows carry point_hash_bytes_per_iteration with 64 hash bytes per key next to their 16 logical output bytes per key, and a new main collection missing it on those rows fails; the single-key full-domain Merkle row reports different fields. Native items_per_second is cross-checked on CPU against cpu_time and on GPU against the manual event time, each raw repetition on its own, and never overwrites the wall-normalized rate. Rows without the schema marker, including historical receipts and unchanged third-party adapters, keep the legacy name-based reading and are marked legacy in the summary.

Reproduce the historical workload and sampling together with --profile publication --workload legacy.

make ptx_info collects current compiler resource reports in build/ptx_info.log. make profile_gpu records an Nsight Systems trace for GPU_PROFILE_BENCH. See the README's Flamegraph section for CPU profiling.

Run third-party comparisons

From a fresh checkout, run:

git clone https://github.com/myl7/fss.git
cd fss
export PATH=/usr/local/cuda/bin:$PATH
export CUDA_HOME=/usr/local/cuda
python3 third_party/bench.py list
python3 third_party/bench.py prepare --platform all
python3 third_party/bench.py build --platform all --cuda-arch 120 --jobs 4
# Short runs validate initialization and output collection. They omit long EvalAll cases.
# The smoke profile defaults to the current library only, so name the suite explicitly.
python3 third_party/bench.py run --libraries all --platform all --cuda-arch 120 --cpu 24 --gpu 0 \
--no-build --smoke --run-id smoke
# Full comparison runs. The publication profile restores the historical
# selection (every library) and five repetitions for Google Benchmark and Python;
# the default decision profile would run the current library only.
python3 third_party/bench.py run --profile publication --platform cpu --cpu 24 --no-build --run-id comparison-cpu
python3 third_party/bench.py run --profile publication --platform gpu --cpu 24 --gpu 0 --no-build --run-id comparison-gpu

Replace 120, 24, and 0 with the GPU architecture, an idle allowed CPU, and the GPU index on your host. --jobs defaults to four to limit build load. --libraries accepts comma-separated names from list, so a single library can be prepared, built, and run without the rest of the suite:

python3 third_party/bench.py prepare --libraries libfss --platform cpu
python3 third_party/bench.py run --libraries libfss --platform cpu --cpu 24 \
--filter 'DPF/(Gen|Eval)$' --run-id libfss-point

Every run pins the host process with taskset and sets OMP_NUM_THREADS=1 and RAYON_NUM_THREADS=1. The default governor policy is performance. The runner reads the previous governor, switches it if required, verifies it before measurement, and restores it on success, failure, or handled termination. If writing the governor requires privilege, configure noninteractive sudo for that write. A missing governor interface or failed switch stops the run. --governor keep is an explicit alternative for smoke checks or hosts with externally managed clocks. Its actual governor is recorded with the results.

The compatibility bench_*.sh scripts use the same runner and accept native benchmark arguments. CPU_ID, GPU_ID, CUDA_ARCH, and JOBS set defaults:

CPU_ID=24 bash third_party/bench_libfss.sh --benchmark_filter='DPF/Gen'

--min-time controls Google Benchmark's measurement window and Criterion's measurement time. Criterion reports its median estimate from 100 samples, or ten in smoke mode. --repetitions applies to Google Benchmark and Python. Do not compare a smoke result with a full measurement.

Each run creates a new build/third_party/results/<run-id>/ containing:

  • run.json: hardware, declared library versions, compiler and tool versions, governor, device selection, timing parameters, commands, and process status.
  • Per-library logs and raw Google Benchmark JSON, Criterion estimates and samples, or Python timings and validation results.
  • summary.csv and summary.md: normalized times, keys per iteration or call, throughput, measurement boundaries, and any failed processes.

The raw JSON and normalized CSV/JSON retain the field name batch for compatibility. It records keys per timed iteration or call, or PRG calls for raw AES rows. It does not record CUDA threads per block.

Rebuild a report from copied results with:

python3 third_party/bench.py summarize build/third_party/results/comparison-gpu

The runner preserves partial results and returns nonzero if any process fails. Historical fss 0.7.0 uses separate binaries and PRG providers for each scheme and group on both CPU and GPU. DPF requires a 32-byte PRG output, while DCF requires 64 bytes. Sharing the DCF provider with DPF would overrun its scratch buffer. The wrappers check both-party reconstruction and guarded scratch buffers before timing. GPU operations run in separate processes so the pinned uint DCF alignment failure does not prevent other measurements. That failure remains visible in the report. EzPC registers 1024 and 262144-key Gen/Eval cases, but only the 1024-key full-domain reduction to keep the traversal bounded.

The main selection runs src/bench_cpu.cu and src/bench_gpu.cu for the README. It is excluded from --libraries all because its groups and operations differ from the comparison harness. Use --libraries main to refresh that separate set of results.

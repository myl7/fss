Benchmark coverage

What the bench_cpu and bench_gpu binaries built by BUILD_BENCH=ON measure, and the GPU kernel resource usage behind them. Build and run instructions are in the README. Measurement methodology, timing boundaries, and the cross-library comparison curves live in benchmark curve methodology. Exact measured values are on the comparison site.

Coverage

  • Schemes: DPF, DCF, VDPF, Half-Tree DPF, packed HalfTree DPF, Grotto DCF, HalfTree Grotto DCF, DMPF, and VDMPF.
  • Operations: Gen, Eval, host EvalAll, VDPF Prove and the Merkle-fold ProveMerkle/EvalAllMerkle, Grotto DCF Preprocess and PreprocessEvalAll, GPU point eval, and full-domain GPU EvalAll for DPF, HalfTree DPF, packed HalfTree DPF, DCF, and VDPF, plus GPU point eval for Grotto DCF and HalfTree Grotto DCF, GPU Grotto DCF Preprocess and EvalAll, and GPU DMPF batch Eval and EvalAll. The lean host point-evaluation fast paths (fss::cpu packed-key walks for DPF and HalfTree DPF, bit-exact with the generic Eval) carry their own rows beside the generic point Eval.
  • PRGs: AES-128 MMO over OpenSSL, AES-128 MMO over AES-NI intrinsics, software AES-128 MMO, and ChaCha. The CPU benchmarks cover all four. The GPU benchmarks cover ChaCha and software AES-128 MMO, the two that run on device.
  • Output groups: Uint and Bytes.
  • VDPF hashes: SHA-256 and BLAKE3.
  • Input domain sizes: 2^20 by default, plus 2^14 and 2^17 for DPF Eval.

Benchmark names follow BM_<Scheme><Operation>_<Group>_<Prg>/<bits>: for example, BM_DcfEval_Uint_AesRaw/17 times one DCF evaluation in the Uint group with the AES-NI-intrinsics PRG over a 2^17 domain. The PRG suffixes are Aes (OpenSSL MMO), AesRaw (AES-NI intrinsics MMO), AesSoft (software AES-128 MMO), and ChaCha. Grotto DCF and VDPF benchmarks omit the group because they have one native output shape. Names without a suffix are template instantiations that differ in input domain bits through the benchmark argument.

The PRG drives most of the difference. Software AES-128 MMO costs about 1.8x the registers of ChaCha for the same scheme and group and is the only backend here with a T-table in shared memory (see the software AES study). The mul parameter is part of the PRG type because it sets how many 16B blocks one Gen call produces. All kernels shown have zero spill stores and zero spill loads. The (z=...) rows are the deep-frontier tilings the Python bindings dispatch to for domains above a 16-bit frontier (25-bit domain shown, per-thread tail depth 4).
